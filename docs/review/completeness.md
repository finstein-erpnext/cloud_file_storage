## [SEVERITY: BLOCKER] [CONFIRMED] Public-file serving via `page_renderer` is silently defeated by frappe's `website_404` negative cache — and the failure is invisible in dev/CI

- **Evidence:**
  - `RT:389`: `PublicFileRenderer.can_render(path)` is the *entire* public miss path; `RT:16` (ADR-6) "a public miss **does** reach Python in production".
  - `frappe/website/path_resolver.py:32-34`: `if request.url and can_cache() and frappe.cache.hget("website_404", request.url): return self.path, NotFoundPage(self.path)` — this returns **before** `custom_renderers = self.get_custom_page_renderers()` at `path_resolver.py:56-60`.
  - `frappe/website/page_renderers/not_found_page.py:23-25`: `if self.can_cache_404(): frappe.cache.hset("website_404", self.request_url, True)`.
  - `frappe/website/utils.py:52-59`: `can_cache()` returns **False when `frappe.conf.developer_mode`** — i.e. every dev bench and every CI site — and **True in production**.
  - Neither `RT §8.2`, `DEL §3`, nor the plan (`plan:216-220`) mentions `website_404`, `clear_website_cache`, or `frappe.local.no_cache`.
- **Why it breaks the plan:** any `/files/...` URL that 404s exactly once in production is permanently pinned to `NotFoundPage` and the renderer is never consulted again. This is guaranteed during cutover (browser/CDN requests a public asset in the window between local quarantine and CSO link, during an S3 blip where the renderer declines, or while the app sits in `LOCAL_ONLY` before P3 ships). Mission requirement (1) "public serving" then fails permanently for those URLs, and the entire test matrix (`DEL §4.1` T-PUB, L2/L3 CI sites run with `developer_mode`/`allow_tests`) can never reproduce it.
- **Suggested fix:** in `PublicFileRenderer` set `frappe.local.no_cache = True` for `files/*` paths, and add an explicit invalidation hook (`frappe.cache.hdel("website_404", url)`) in `write_file`, `handle_is_private_changed`, and the migration VERIFY link transaction. Add a T-row asserting renderer reachability with `can_cache()` forced true (`frappe.flags.force_website_cache`).

## [SEVERITY: BLOCKER] [CONFIRMED] The runtime↔migration CSO interface is mismatched in field names, status vocabulary and function names — and no "Principal ruling" covers it

- **Evidence:**
  - Status case: `RT:196` CSO `status` Select is `pending_upload\nuploaded\nverified\nfailed\norphaned\npending_delete\ndeleted\nlegacy_unverified`; `RT:371` serving gate is `if cso and cso.status in ("uploaded", "verified", "legacy_unverified")`. `MIG:403` `... AND status='Verified'`; `MIG:405` `status="Uploaded"`; `MIG:432` "CSO status `Verified`"; `MIG:472` "status `Verified`".
  - Field names: `MIG:403` `SELECT name FROM tabCloud Storage Object WHERE sha256=%s AND size=%s`; `MIG:489` `WHERE object_key IN (...)` — the CSO columns are `content_sha256` (`RT:183`), `file_size` (`RT:185`), `s3_key` (`RT:190`).
  - Function names: `MIG:405` `get_or_create_cso(provider, bucket, key, sha256, md5, size, mime, visibility, source_path, etag, version_id, status="Uploaded")` and `MIG:403` `adopt_references(cso, n)`; the runtime API is `ensure_cso(sha256, md5, size, mime, visibility)` (`RT:432`, `RT:48`) — neither `get_or_create_cso` nor `adopt_references` exists anywhere in `RT`.
  - The plan's ruling list (`plan:329-360`) rules on doctype *names* (ruling 2), backup config (3), settings schema (4), multipart (5) — **nothing** on CSO status vocabulary, column names, or the migration→runtime call surface.
- **Why it breaks the plan:** the migration engine is the single largest deliverable and its only interface to the runtime layer is this API. As written, the dedup query and reconcile query raise `Unknown column 'sha256'`/`'object_key'`, and every CSO the engine writes lands in a status string (`Verified`) that `RT:371`'s serving gate and `RT:273`'s `exists_on_disk` will never match — i.e. all 1.2M migrated private files would 404 after cutover while the campaign reports 100% verified. The `legacy_unverified → verified` transition in `RT:226` is also orphaned: adoption (`MIG:472`) never produces that status.
- **Suggested fix:** add a binding ruling: CSO statuses are lowercase snake_case exactly as `RT:196`; columns are `content_sha256`/`content_hash_md5`/`file_size`/`s3_key`; the only runtime entry points are `ensure_cso()`, `adopt_references()`, `set_cso_status()`, `engine.verify()` with signatures frozen in P2 and imported (never inlined SQL) by `migration/`. Add a P5 gate test that asserts a migration-created CSO is servable through `serving/private.py`.

## [SEVERITY: BLOCKER] [CONFIRMED] The materialization write-back mechanism runs in hooks that fire *after* frappe has already committed/rolled back — its DB writes are discarded

- **Evidence:**
  - `RT:99-100`: `after_request = ["...cache.writeback.flush_request"]`, `after_job = ["...cache.writeback.flush_job"]`. `RT:347`: flush "→ relink `File.cloud_storage_object`, update `content_hash`, `file_size` via `db_set(update_modified=False)` → decrement old CSO" — no commit mentioned.
  - `frappe/app.py:139-155`: `else: rollback = sync_database(rollback)` … then `finally:` … `run_after_request_hooks(request, response)`. `frappe/app.py:416-423`: `sync_database` does `frappe.db.commit()` for unsafe methods **or `frappe.db.rollback()` otherwise**, i.e. the transaction is finalized *before* the hook runs; nothing commits afterwards (`frappe.destroy()` → `db.close()`, `frappe/__init__.py:423-428`).
  - `frappe/utils/background_jobs.py:255-265`: `else: frappe.db.commit(); return retval` … `finally: for after_job_task in frappe.get_hooks("after_job"): frappe.call(...)`. The research report already recorded this ordering (`research/frappe-jobs-backups.md:117`: "`after_job` after, in `finally` … commit on success (`:256`)") but neither design drew the consequence.
  - `frappe/app.py:150-155` also swallows hook exceptions: `except Exception: frappe.logger().error("Failed to run after request hook")` — contradicting `RT:446` "never swallowed".
- **Why it breaks the plan:** contract invariants #7/#8 (mission area 1 "local materialization", area 6 "no DFP-style breakage", the erpnext `stock_ledger.py:420-422` and `bank_statement_import.py:202-212` write-through callers the plan calls out at `plan:121-122` and `RT:347`) depend entirely on write-back persisting. As designed, the new CSO is uploaded to S3 but the `File` row is never repointed — permanent silent divergence between DB pointer and bytes, in exactly the flow ADR R9/T-RIV claims to make safe.
- **Suggested fix:** end `flush_request`/`flush_job` with an explicit `frappe.db.commit()` (and re-open a transaction for the GET case where `sync_database` already rolled back), wrap the body in its own try/except that writes an Error Log, and make contract test C8 assert persistence by re-reading the `File` row in a *new* transaction. Alternatively move write-back to `frappe.local.request.after_response`/`frappe.local.job.after_job` CallbackManagers, which have the same ordering problem — so the explicit commit is required either way.

## [SEVERITY: MAJOR] [CONFIRMED] Legacy adoption creates CSO rows that violate the CSO schema's mandatory fields

- **Evidence:** `RT:183-184`: `content_sha256` "reqd, read_only", `content_hash_md5` "reqd, read_only". `MIG:472`: "`md5 = ETag if '-' not in ETag else NULL` … `sha256=NULL` … status `Verified`".

## [SEVERITY: MAJOR] [CONFIRMED] `Cloud File URL Alias.old_url` is a 140-char column with an impossible 191-byte prefix index

- **Evidence:** `MIG:214`: "`old_url | Data, reqd, unique (index old_url(191))`". `frappe/database/mariadb/database.py:192` maps `Data` → `("varchar", self.VARCHAR_LEN)` (140 unless an explicit `length` is set — `frappe/database/schema.py:133` `new_length = cint(col.length) or cint(frappe.db.VARCHAR_LEN)`), and frappe's `unique: 1` emits `ADD UNIQUE INDEX (col)` with no prefix (`frappe/database/mariadb/schema.py:76`).
- **Why it breaks the plan:** the DDL is invalid (key part longer than column), and even after fixing it, the URLs this table exists to alias — `/api/method/frappe_s3_attachment.controller.generate_file?key=<long content-addressed key>&file_name=<name>` — routinely exceed 140 chars and would be truncated, so alias lookups silently miss.
- **Suggested fix:** `old_url`/`new_url` → `Data` with explicit `length: 500` (or `Small Text` + a separate `url_hash Data(40) unique`), and index on the hash, not the URL.

## [SEVERITY: MAJOR] [CONFIRMED] Backup: `hot_retention_days` is a dead field and there is no per-frequency (hourly vs daily) retention

- **Evidence:** `DEL:186` defines `hot_retention_days` Int default 14 "stays STANDARD". `DEL:223-227` `build_lifecycle_policy` emits exactly four rules — `cfs-archive` (`Days=archive_after_days`), `cfs-expire` (`Expiration.Days=delete_after_days`), `cfs-noncurrent`, `cfs-abort-mpu`. `hot_retention_days` appears nowhere in the generated policy; its only use is validator rule 4 (`DEL:235`, "`hot_retention_days > archive_after_days` ⇒ error"). `DEL:179` offers `frequency` `Hourly\nEvery 6 Hours\nDaily\nWeekly` but all backups land under one `backup_prefix` (`DEL:172`) with one `Expiration.Days`.
- **Why it breaks the plan:** mission area (7) requires hourly *and* daily retention plus hot/total/archive/delete-age/noncurrent as *distinct* controls. ## Verdict

**Not implementable as written — but the gap is editorial, not architectural.** The architecture is sound and unusually well-grounded: the seam choice, content-addressed keys, deferred refcounted GC, DB-as-source-of-truth migration engine, and the anti-DFP `get_content` superset are all correct against v15.93 and I could not refute any of the load-bearing framework claims. What fails is the *synthesis*: the plan's eight "Principal rulings" resolve the cross-design conflicts that were easy to spot (doctype names, TTLs, multipart) and miss the ones that actually cost implementation days — the CSO status/column/API vocabulary that is the sole interface between P2 and P5, the campaign state machine the entire button contract is written against, the settings fieldnames P6/P7 will code against, and the three-way `generate_file` path split. On top of that, three verified framework behaviors are unaccounted for anywhere in plan or designs: the `website_404` negative cache (which silently kills public serving in production while being structurally invisible to the whole test matrix), the `after_request`/`after_job` post-commit ordering (which makes the materialization write-back — the mechanism the plan leans on for erpnext/IC compatibility — a no-op), and the `Data(140)` ceiling on the alias table. Mission coverage is otherwise strong: all 4 modes, all 15 CSO attributes, all 9 detection classes, the phase/queue/batching constraints, the destructive-action confirmations, and the deliverable set are present; the material completeness gaps are per-frequency backup retention, six missing T-rows against the plan's own "full matrix" claim, contract tests running on one frappe revision instead of three, and the absence of worktree/branch isolation and commit discipline in the autonomous-execution rules. Fix the three BLOCKERs and publish a single frozen interface table (CSO API + statuses, campaign statuses, Settings fieldnames, endpoint dotted paths) as a binding ruling before P2 opens, and the plan becomes executable.
