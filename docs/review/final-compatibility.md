## OPEN BLOCKERS

**B1 — [CONFIRMED] Floor version claim `v15.0.0` is false for the entire private-serving design (dimension 6 + 8).**
Evidence: `frappe/core/doctype/file/utils.py:430` `find_file_by_url` **does not exist at `v15.0.0`** — it was introduced by commit `3211ccf1da` ("Private images in PDFs from background jobs"), first tagged **v15.16.0**. At the floor, `frappe/utils/response.py:257-273` (v15.0.0 tree) has a completely different body: no `frappe.form_dict.fid` support, no `if frappe.session.user == "Guest": raise Forbidden` (that landed 2024-01-30, first tag **v15.13.0**), and it inlines the readable-row loop instead of delegating.
Why A1-A24 don't cover it: the plan's floor verification is explicitly scoped to "both hooks + before_request + deduplicate-enqueue + filelock" (plan line 322-323) — the serving surface was never checked. A22 only mandates *running* C1-C19 on all three refs; it does not reconcile the incompatibility. `serving/private.py` as designed (`design/runtime-storage.md:359-372`) does `from frappe.core.doctype.file.utils import find_file_by_url` + `frappe.form_dict.fid` inside the patched function → **ImportError at request time on any floor-range site with the app active**, i.e. HTTP 500 on every `/private/files/*` request, and the C10 contract test cannot pass at the floor ref.
Minimal fix: either raise the declared floor to **v15.16.0** (CI matrix + `supported-versions.md` + `frappe-dependencies >=15.16.0,<16.0.0`), or make `runtime_patches` feature-detect (`getattr(frappe.core.doctype.file.utils, "find_file_by_url", None)`) and fall back to an inlined replica of the pre-15.16 gate (loop + `is_downloadable`, ignore `fid`, explicit Guest deny). Add a floor-ref serving test that actually exercises `/private/files/`.

**B2 — [CONFIRMED] Serving resolves the CSO by own-link only; the A1 `_resolve_cso` chain is not applied there, so legitimately-unlinked File rows become unservable once local copies are gone (dimension 8 + 5).**
Evidence: A1 (plan:378-387) enumerates a *closed* consumer list — `_is_cloud_backed`, `_read_bytes`, `exists_on_disk`, `validate_file_on_disk`, `get_full_path` — serving is not in it. `design/runtime-storage.md:265` defines `_cso()` as "cached `frappe.get_doc` of `self.cloud_storage_object`" (own link only) and `design/runtime-storage.md:370` uses exactly that in the patched `download_private_file_cloud`; `design/runtime-storage.md` §8.2 has `PublicFileRenderer.can_render` do a single `frappe.db.get_value("File", {"file_url": ...}, ["name","cloud_storage_object"])`. Meanwhile `frappe/core/doctype/file/utils.py:435-443` `find_file_by_url` returns the **first readable row** among all rows sharing the URL — order is unspecified, so it routinely returns a sibling other than the linked one. Unlinked-but-valid rows are generated by `frappe/core/doctype/file/file.py:686-702` (dedup branch: `file_exists=True` ⇒ the `write_file` hook is never called) and `frappe/core/doctype/file/utils.py:362-372` (`attach_files_to_document` URL-only insert, exceptions swallowed at `:373-374`).
Why A1-A24 don't cover it: `doc_events.file_after_insert`/`ensure_cso_link` (design §6.3) closes most of this at insert time, but only by matching a sibling with **`content_hash` + `is_private` + non-empty link**. During the 1-2 day live migration the sibling is frequently not yet linked (File↔CSO linkage happens only inside the VERIFY-success transaction, plan:257), so rows created in that window keep `cloud_storage_object = NULL` forever; A1 makes their *reads* work (chain step 2: sibling by `file_url` + link) but serving still uses `_cso()` → private = `raise NotFound`, public = renderer declines → 404 that is then written into the `website_404` hash (`frappe/website/path_resolver.py:34`, `frappe/website/page_renderers/not_found_page.py:24`) and short-circuits every later request before any renderer runs.
Minimal fix: use `_resolve_cso()` (not `_cso()`) in `serving/private.py`, and make `PublicFileRenderer.can_render` treat the URL as cloud-backed if **any** row sharing `file_url` resolves a CSO (keeping A19's `is_private = 0` check on the resolved row); add the "unlinked sibling created mid-campaign" case to T-ALIAS/T-PRIV.

**B3 — [CONFIRMED] India Compliance `upload_gstr` (GSTR-2A/2B JSON ingest) reads through `frappe.utils.file_manager.get_file_path`, which never touches the File doc and cannot be intercepted by any seam in the plan (dimension 7).**
Evidence: `india_compliance/gst_india/doctype/purchase_reconciliation_tool/purchase_reconciliation_tool.py:112-121` `upload_gstr(...)` → `get_json_from_file(file_path)` (`india_compliance/gst_india/utils/__init__.py:671-672`) → `frappe.utils.file_manager.get_file_path` (`frappe/utils/file_manager.py:346-378`), which resolves `file_url` by raw `frappe.qb` and returns a **local** path (`frappe.throw` on anything non-`/files/`), then `frappe.get_file_json` → `open()`. The research ground truth flagged this as consumer #13 and invariant-19 note (`research/content-consumers-contract.md:74`, `:104`, `:19-19`), but no invariant, no A-amendment, and no design section addresses it.

Breaks as soon as migration CLEANUP removes local copies (any mode), and permanently in `S3_PRIMARY_LOCAL_FALLBACK` / `S3_ONLY`.
Minimal fix: in `runtime_patches`, patch **both** `frappe.utils.file_manager.get_file_path` and (guarded on `"india_compliance" in frappe.get_installed_apps()`) `india_compliance.gst_india.utils.get_file_path` to resolve the File row and return `file_doc.get_full_path()` (materialized); OR — cheaper and A17-consistent — ship `Purchase Reconciliation Tool` in the default `ignored_doctypes` so those attachments stay local, and add a T-IC-LIVE case that runs `upload_gstr` after cleanup. Same patch also fixes `erpnext/edi/.../code_list_import.py:30` and `common_code.py:89`.

## OPEN RISKS
1. Print/PDF public images: only *private* images are inlined (`frappe/utils/pdf.py:269-294` → `get_content()`, exceptions logged and dropped); public `/files/*` images (letterhead, company logo, item images, e-Waybill PDFs) are still fetched over HTTP by wkhtmltopdf → 302 to presign/CDN requires outbound HTTPS + redirect-following from every app/worker host, and failures silently produce image-less PDFs.
2. A11's alias insertion point is wrong for private serving: `find_file_by_url` miss raises **Forbidden** (`frappe/utils/response.py:271-274`) long before the `raise NotFound` the amendment names, so aliased old URLs would 403; the alias must be consulted at the miss and the permission gate re-run on the resolved target *before* redirecting (otherwise a 302-vs-403 split also discloses file existence).
3. Two other local-path-only readers degrade silently in S3_ONLY: `frappe/email/email_body.py:553-576` `get_filecontent_from_path` (inline email images are stripped) and `frappe/utils/data.py:1484-1497` `pdf_to_base64` (Jinja helper in print formats).
4. Legacy adopted rows with NULL `content_hash` never reach the delete hook at all (`frappe/core/doctype/file/file.py:511-517` short-circuits on falsy `content_hash`), so their CSOs are never decremented — permanent orphan objects, relying entirely on the reconcile/orphan sweep for cost control.
5. A URL-only File insert performs **two** full-object S3 GETs (`file.py:106` `save_file(content=self.get_content())`, then `file.py:658-659` `flags.original_content = self.get_content()` because `flags.new_file` is set only at `file.py:107`), and pins the whole payload in RAM for the request — amend/copy of large attachments doubles egress and memory.
