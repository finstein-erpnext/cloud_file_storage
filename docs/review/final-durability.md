## OPEN BLOCKERS

**B1. `ensure_cso()` returns `deleted` tombstones, so re-uploading previously-GC'd content silently never sends bytes to S3.** — [CONFIRMED]
- Evidence: `design/runtime-storage.md:432` (`ensure_cso` — "found → return"; only `pending_delete` resurrection is described), `:308` (write path: "if new or `pending_upload`/`failed` → upload now"), `:222` + `:446` (GC leaves a **`deleted` tombstone row**), `:206-210` (UNIQUE `(content_sha256, visibility, bucket)` and UNIQUE `(s3_key)` — the tombstone permanently occupies the dedup identity, so no fresh CSO row can be inserted for that content).
- Failure: user attaches invoice.pdf → deletes it → GC physically deletes after `object_delete_grace_days` (7) → user re-attaches the identical file. `ensure_cso` finds the tombstone, status is `deleted` (not new/`pending_upload`/`failed`), the upload branch is skipped, `file.cloud_storage_object` is set, `write_file` returns success. In S3_PRIMARY/S3_ONLY no local copy exists ⇒ the bytes are never stored anywhere; every later read is a 404/`CloudObjectNotFound`.
- Why A1-A24 don't cover it: A15 constrains resurrection semantics only for `pending_delete` ("restores the **prior** status"); A6/A14 govern when GC may delete; A7 freezes `deleted` as a legal status. No amendment says what `ensure_cso` does when it finds a `deleted` (or `orphaned`) row, and the upload trigger list in `:308` is unchanged.
- Minimal fix: make the upload gate positive — upload unless status ∈ {`uploaded`, `verified`, `legacy_unverified`}; on finding `deleted`/`orphaned`, transition back to `pending_upload` (clearing `deletion_scheduled_at`, keeping the tombstone's audit fields) under the same lock, then PUT. Add contract test: delete → force GC → re-upload identical bytes → object exists in bucket and `get_content()` returns them.

**B2. The VERIFY link write is an unconditional `UPDATE … SET f.cloud_storage_object`, clobbering any relink the runtime made after UPLOAD.** — [CONFIRMED]
- Evidence: `design/migration-engine.md:419-422` (`UPDATE tabFile f JOIN tabCloud Migration File Ref r ON r.file=f.name SET f.cloud_storage_object=%(cso)s WHERE r.migration_object=%(obj)s` — no predicate on the File's current link, `content_hash`, or `file_url`); ADR-M10 `:22`; the design's own claimed mitigation at `:526` ("File mutated during migration → VERIFY hash mismatch → Conflict") is **false**: `:414-417` shows VERIFY compares the *remote* object against the hash recorded at upload, never the local/current File state, so a mutated File verifies clean.
- Failure: campaign in S3_PRIMARY_LOCAL_FALLBACK. T1 UPLOAD of File X (bytes A → CSO-A). T2 `gst_return_log.py:103`-style `save_file(content=B, overwrite=True)` → runtime creates CSO-B and persists the relink (A2). T3 VERIFY of CSO-A succeeds → the UPDATE-JOIN repoints X back to CSO-A. CSO-B now has zero `tabFile` references and is not owned by any migration object (A14 doesn't protect it) ⇒ GC `pending_delete` → physical delete after grace. **Bytes B are destroyed** and X silently serves stale A while `content_hash` still holds md5(B). Same UPDATE also re-points a File that flipped to private (A16 path) back at the `pub/`-prefixed CSO — a privacy regression A16 explicitly fixed on the runtime side.
- Why A1-A24 don't cover it: A2 fixes runtime-side persistence, A4 fixes local-bytes re-check at CLEANUP (which only saves DUAL_WRITE, where a local copy of B exists), A16 fixes the runtime visibility flip, ruling #8 sanctions this exact raw UPDATE **without adding a guard**. Nothing constrains the migration engine from overwriting a newer runtime link.
- Minimal fix: add `AND (f.cloud_storage_object IS NULL OR f.cloud_storage_object = %(cso)s) AND f.file_url = r.file_url AND (f.content_hash IS NULL OR f.content_hash = %(md5)s)` to the UPDATE, compare `ROW_COUNT()` against the ref count, and route non-matching refs to `Skipped(superseded_by_runtime)` (never `CleanupEligible`) plus an audit row.

**B3. Post-cutover restores are silently incomplete: DB-only backups (365-day retention) vs a 7-day object grace, with no versioning requirement on the attachment bucket.** — [CONFIRMED]
- Evidence: `design/delivery-platform.md:158` (B2 — always `ignore_files=True`; file tarballs default off and "warned against post-cutover"), `:2.2(c)` (advises removing `--with-files` cron entries), `design/runtime-storage.md:444` ("versioning **optional**"), `:163`/plan A12 (`object_delete_grace_days` 7) vs `delivery-platform.md:2.1` (`delete_after_days` 365); recovery tooling is restore-of-the-*backup*-artifact only (`:240-249`), and reconcile only *alerts* on missing-remote (`migration-engine.md:490`).
- Failure: any `bench restore` of a dump older than 7 days brings back File/CSO rows whose objects GC physically deleted in the interim (and whose quarantine copies were purged at 14 days). The site comes up "clean" — every consumer (`get_content`, GST return log, e-Waybill) then hits a missing object. There is no PITR coupling between the DB snapshot and the bucket, and nothing verifies the downloaded artifact's SHA256 against `Cloud Storage Backup Log.sha256_manifest` before restore either.
- Why A1-A24 don't cover it: A5 verifies backup artifacts *at upload*; A20 scopes/merges lifecycle rules on the *backup* bucket. Neither addresses that the site's file bytes have left the backup set entirely.
- Minimal fix: (a) `Cloud Storage Settings.validate()` asserts `object_delete_grace_days >= restore_window_days` (new field, documented as the guaranteed recoverability window) and surfaces it in the health panel; (b) require (or hard-warn on) bucket versioning + `NoncurrentVersionExpiration >= restore_window_days` on the attachment bucket, checked by `test_connection`; (c) restore runbook step: download → SHA256 compare vs Backup Log → then `bench restore`.

**B4. The scheduled backup calls `new_backup()` with the default `older_than=6, force=False`, so it can re-upload a stale dump and report Success.** — [CONFIRMED]
- Evidence: `design/delivery-platform.md:209` (`new_backup(ignore_files=not (pub or priv), compress_files=...)` — no `force`), against real code `frappe/utils/backups.py:587-626` (`older_than=6`, `force=False`) → `:164-209`: if `last_db and last_file and last_private_file and site_config_backup_path` are all within the window it **skips the dump** and sets `self.backup_path_db = last_db`. `frappe/commands/site.py` always passes `force=True` — our design is the only caller that doesn't.
- Failure: any site where file tarballs exist within 6h (bench crontab `--with-files`, a manual `bench backup --with-files`, or one run with the design's own `include_*_files` checkboxes on) — the Hourly job uploads the same 6-hour-old dump under a new timestamped key each hour; A5 verification passes (it verifies the transfer, not freshness), `last_backup_status=Success`, `last_backup_on=now`. Believed RPO 1h, actual up to 6h+, with N identical artifacts consuming retention/lifecycle.
- Why A1-A24 don't cover it: A5 is upload verification; A20 adds per-frequency prefixes/expiration. The reviewed "stale-backup trap" was the *other* one (`s3_backup_settings.validate_file_size`'s >1GB flag, `research/frappe-jobs-backups.md:173`), so this one was never examined.
- Minimal fix: `new_backup(..., force=True)`; assert the returned `odb.backup_path_db` mtime ≥ job start before logging Success.

**B5. The quarantine layer is specified in two lines that both admit a data-destroying reading.** — [SUSPECTED]
- Evidence: `design/migration-engine.md:21` (ADR-M9: quarantine into `private/cloud_migration_trash/<campaign>/`) + `:434` (`os.rename(disk_path, quarantine_path)`) + `:435` (`purge_expired_quarantine`: "deletes quarantine **files older than TTL**").
- Failure (a): a flat per-campaign directory receiving up to 1.2M files collapses `public/files/x.pdf` and `private/files/x.pdf` onto one target; POSIX `rename` **silently replaces** the existing target, so the first file's rollback copy is destroyed and the `local_quarantine` audit row now points at a path holding different bytes — an operator "restore from quarantine" writes the wrong content back over the original path. Failure (b): `os.rename` preserves mtime, so a TTL computed from filesystem age purges a file quarantined 10 minutes ago if the attachment is 14+ days old — i.e. the entire 14-day rollback window silently evaluates to zero for essentially the whole corpus.
- Why A1-A24 don't cover it: A4 hardens the pre-quarantine check, A17 removes thumbnails from cleanup; nothing specifies the quarantine path layout or the purge key.
- Minimal fix: quarantine path = `<trash>/<campaign>/<migration_object_name>` (or mirror the source relative path), refuse to rename if the target exists; purge selects on `Cloud Migration Object.status='Quarantined' AND cleaned_at < now - ttl` and stats the row's recorded path — never `os.listdir` + mtime.

## OPEN RISKS
1. CLEANUP's pre-delete HEAD re-verification (`migration-engine.md:433`) has no `<64MB` / `≥64MB` strategy switch — A12 wired `verify_strategy_cutover_mb` into VERIFY only, so multipart objects either permanently block cleanup or silently degrade to a size-only check.
2. A14's "GC excludes CSOs owned by non-terminal campaigns" has no supporting index: `Cloud Migration Object`'s frozen index set (`migration-engine.md:167-172`) lacks `cloud_storage_object`, making each GC candidate a 1.2M-row scan (a slow/timing-out guard fails open).
3. Batch heartbeat staleness is 10 min while a single large object can exceed it (heartbeat only ticks between objects, `:398`) → dispatcher resets a live batch; a second worker plus the first's `_finalize_upload_batch` can mark a batch `Uploaded` with objects still in flight, and a campaign can reach `Completed` with non-terminal stragglers.
4. `AbortIncompleteMultipartUpload` on the **attachment** bucket is documentation-only (A20/B5 restrict the generator to the backup bucket, and `s3.upload_file` never exposes an `UploadId` for the promised `finally` abort) — SIGKILL-orphaned parts accumulate unbounded and unmonitored.
5. During an S3 outage >24h, hourly `take_cloud_backup` keeps generating local dumps that core's `delete_temp_backups`/`keep_backups_for_hours` removes, and nothing re-uploads a previously-failed artifact — a permanent hole in the offsite timeline plus local disk pressure exactly when the site is degraded.

## OPEN BUSINESS DECISIONS
1. **Declared recovery window**: how far back must a restore reproduce *attachments*? This is the input to B3 — it sets `object_delete_grace_days`, whether the attachment bucket must run versioning/CRR (recurring cost), and what "365-day backup retention" is actually allowed to promise.
2. **DR ownership after cutover**: does the app's hourly DB backup supersede the bench crontab, and who is accountable for the attachment bucket's durability posture (versioning, MFA-delete, cross-region replication) now that 100GB of business documents exist in exactly one place?
3. **Cleanup destructiveness policy**: whether `Direct Delete` cleanup mode may ever be enabled in production, and whether 14 days of quarantine (≈100GB of retained local disk) is the right trade against reclaiming space sooner.

## VERDICT
**BLOCK** — for data-loss, cleanup safety, crash recovery, and backup/restore. A1-A24 genuinely close the round-1 spine (write_file persistence, write-back commit discipline, URL-only resolution, locking recount, campaign-owned CSOs, ignored-doctype scoping, lifecycle scoping), and I could not break those fixes. What remains are four confirmed silent-loss paths the amendments never touch: a `deleted` CSO tombstone that turns a re-upload into a no-op (B1), a migration VERIFY link write that overwrites newer runtime relinks and then lets GC destroy the newer bytes (B2), a post-cutover backup set that no longer contains file bytes with no coupling between DB restore points and object lifetime (B3), and a scheduled backup that can ship a 6-hour-old dump as Success (B4). Each fix is local — an extra status branch, a WHERE clause, `force=True`, and a recoverability-window validator — so I expect a fast re-approval once they are recorded as binding amendments (A25-A29) with the quarantine path/purge-key specification (B5).
