## OPEN BLOCKERS

**B1. `deleted` CSO tombstones poison `ensure_cso` — a re-uploaded file is silently linked to an object that no longer exists in S3. [CONFIRMED]**
- Evidence: `(internal evidence path):222` (`pending_delete → S3 delete → deleted (tombstone)`), `:432` (`ensure_cso`: "found → return (resurrect from `pending_delete` → `verified`)"), `:196` (UNIQUE `(content_sha256, visibility, bucket)`), `:11` in §11 ("GC physical deletes leave `deleted` tombstone rows"), write path `:305` step 4 ("if new or `pending_upload`/`failed` → upload now").
- Why A1–A24 don't cover it: A15 (`(internal planning record):462-466`) only fixes the *status* returned when resurrecting from `pending_delete`; A7 (`:411-417`) freezes `deleted` as a legal status. No amendment says what `ensure_cso` does when the identity row it finds is `deleted`. The unique index guarantees a new row cannot be inserted, so `ensure_cso` returns the tombstone, the upload branch is skipped (`deleted` ∉ {new, pending_upload, failed}), `File.cloud_storage_object` points at a deleted key, `exists_on_disk()` is False, and `_read_bytes` → S3 404 → `CloudObjectNotFound(FileNotFoundError)` → `india_compliance/gst_india/doctype/gst_return_log/gst_return_log.py:196-199` nulls the business pointer.
- Failure scenario: content X is uploaded, its last File row is trashed, GC deletes the object after grace and tombstones the CSO; a user re-uploads the identical file next week → File row created, no bytes anywhere, pointer later nulled.
- Minimal fix: `ensure_cso` must treat `deleted`/`orphaned` like a fresh row — under the same lock, reset to `pending_upload` (clear `etag/version_id/verified_at`) and force the upload branch; add a contract test "delete → GC → re-upload identical bytes → object present and servable".

**B2. No bounded S3 timeouts and no circuit breaker on the synchronous request path — an S3 outage takes the whole ERP down in every non-`LOCAL_ONLY` mode. [CONFIRMED]**
- Evidence: the only boto tuning in the entire design is `TransferConfig` (`.../design/runtime-storage.md:254`); no `botocore.config.Config` anywhere in the three design docs or in A1–A24. Installed botocore 1.34.162 defaults: `DEFAULT_TIMEOUT = 60` for both connect and read (`botocore/endpoint.py:38`, `botocore/httpsession.py:80`, applied at `botocore/config.py:241-242`) with legacy retry `max_attempts: 5` (`botocore/data/_retry.json:93`). `write_file` performs the PUT inline in the File insert (`.../design/runtime-storage.md:305-311`), i.e. inside the web request.
- Why A1–A24 don't cover it: no amendment mentions timeouts, retry budgets, or a health/breaker flag; `before_write_file` is only described as a config-validity guard ("unreachable-flagged" is asserted but never produced).
- Failure scenario: the S3 endpoint blackholes (DNS/SG/regional event). Each attachment upload blocks a gunicorn worker for up to ~5 × 60 s plus backoff; a handful of concurrent uploads exhausts the worker pool and the site stops serving *everything*, directly contradicting the mode matrix rows `.../design/runtime-storage.md:412,418` ("DUAL_WRITE … fully operational (reads local)"). Same hazard on `get_content`/materialize for reads.
- Minimal fix: one `Config(connect_timeout=3, read_timeout=15, retries={"max_attempts": 2, "mode": "standard"})` client for request-path calls (a separate long-timeout client for migration/repair jobs), plus a Redis-cached breaker that `before_write_file`/serving consult so that after N consecutive transport failures DUAL_WRITE/S3_PRIMARY go straight to the local path and S3_ONLY fails fast with the typed error.

**B3. Transiently-failed migration objects are stranded: the batch advances to VERIFY/Verified and is never re-dispatched for upload, so per-object backoff/retry is dead code. [CONFIRMED]**
- Evidence: `.../design/migration-engine.md:395` (`_finalize_upload_batch` → "failures remain → Uploaded (partial) with objects_failed>0"), `:408` (transient error → object CAS back to `Pending`, `next_retry_at` set), batch state machine `:327-331` (`Uploaded → VerifyDispatched → Verifying → Verified`; the only path back to `Pending` is stale-heartbeat recovery), dispatcher `:373-378` (`_next_batches` … "verify-priority: Uploaded batches before Pending ones"), campaign completion `:320` ("all batches Verified").
- Why A1–A24 don't cover it: A9 freezes the *campaign* state machine and the button table; nothing re-opens a batch whose objects are `Pending`/retry-due. Those objects have no Conflict row either (they are below `max_attempts`), so they are invisible to the conflict queue that A9/A23 test.
- Secondary mechanism, same blocker: `_finalize_upload_batch(batch)` is not a CAS from the claimed state, so after a stale-heartbeat reset (a single object can block far longer than the 10-min threshold given B2's 300 s boto stall while `_heartbeat_maybe` only fires between objects, `:391-394`) a second worker claims the batch and the first worker's finalize still promotes it to `Uploaded`, stranding whatever worker 2 had not finished.
- Failure scenario: a 90-second S3 blip during UPLOAD leaves ~2k objects `Pending` inside batches that then go Verified; the campaign reports "verify done", the operator approves cleanup, and those files are silently never migrated (no byte loss, but the migration under-delivers and only the S3_ONLY gate would later reveal it).
- Minimal fix: `_finalize_upload_batch` must be a CAS `Uploading → Uploaded` that only fires when `COUNT(objects in {Pending, Uploading}) == 0`; otherwise set `Pending` with `attempts+1` (bounded) so the dispatcher re-enqueues upload for the residue; add a campaign-level invariant that VERIFY may not start for a batch with non-terminal upload objects.

**B4. No database-capacity preflight before materialising the ~2.4M-row snapshot on the live production DB. [CONFIRMED gap]**
- Evidence: the only "preflight" in the plan is index creation (`.../design/migration-engine.md:231`) and `head_bucket` for backups (`.../design/delivery-platform.md:202`); `grep -i "free space|disk space|capacity"` over the design and review sets returns nothing else. Snapshot cost is asserted as "1.5–2.5GB … Accepted (ADR-M15)" (`.../design/migration-engine.md:307-309`) and A24 does not add a gate.
- Honest bytes/row (from the actual §2.3/§2.4 schemas + Frappe standard columns, utf8mb4/DYNAMIC): `Cloud Migration Object` ≈ 600 B clustered + ≈ 450 B across the 5 declared indexes *plus* the 4 separate single-column indexes Frappe creates for every `search_index: 1` field ⇒ **≈1.0–1.2 KB/row ≈ 1.3 GB**; `Cloud Migration File Ref` ≈ 270 B + 110 B ⇒ **≈0.4 KB/row ≈ 0.5 GB**. So the table estimate (~1.9 GB) is fair — but the *transient* requirement is not: add ~1M CSO rows (~0.4 GB), the `tabFile.content_hash` index (~50 MB), the `cloud_storage_object` column+index (~60 MB), CLASSIFY's `GROUP BY` temp tables in `ibtmp1` (300–600 MB, never returned to the OS without a restart), and — if `log_bin` is on — row images for ~3.6M inserts and ~2.4M `tabFile` updates ⇒ **6–12 GB of binlog**. Real peak ≈ **10–15 GB free**, 5× the documented figure.
- Failure scenario: the analyzer is started on a prod host with ~4 GB free on the datadir/binlog volume; MariaDB fills mid-scan and the *entire ERP* (not just the migration) goes down or into a crash-recovery state — the worst possible outcome for a migration whose whole premise is "site stays live".
- Minimal fix: gate `start_analysis` on a computed preflight — `est = COUNT(*) FROM tabFile × 1.2 KB × 2`, refuse unless `os.statvfs(datadir).f_bavail ≥ 4 × est` and (when `log_bin=ON`) the binlog volume has ≥ 4 × est, `innodb_file_per_table = 1` (so `cfs-migrate-purge` actually returns space), and a verified DB backup newer than the campaign exists. Record the numbers on the Campaign row.

**B5. `autoname: hash` + bulk `ON DUPLICATE KEY UPDATE` / `INSERT IGNORE` converts a primary-key collision into a silent row merge/drop at 1.2M-row scale. [SUSPECTED]**
- Evidence: `.../design/migration-engine.md:133,178` (both ~1.2M-row tables use `autoname: hash`), `:264` ("upsert objects with `INSERT … ON DUPLICATE KEY UPDATE ref_count = ref_count + VALUES(ref_count)`; bulk `INSERT IGNORE` file refs"). v15 `make_autoname("hash")` = `(_get_timestamp_prefix() + _generate_random_string(7))[:10]` (`/home/user/v15/apps/frappe/frappe/model/naming.py:275-293`): 1 trace char (constant for the whole job) + 3 decisecond chars + **6** base32 random chars ⇒ only 32⁶ ≈ 1.07e9 values per decisecond bucket. A 2000-row page inserted inside one bucket collides with p ≈ 1.9e-3; across ~600 pages × 2 tables the expected number of PK collisions is **order 1, not negligible**.
- Why A1–A24 don't cover it: A24 touches counters, Selects and index placement but not row naming; MySQL's `ON DUPLICATE KEY UPDATE` fires on *any* unique violation including the PRIMARY KEY, so a name collision silently increments an unrelated object's `ref_count` and the new object row never exists — while the File Ref rows already carry `migration_object = <that colliding name>`. At VERIFY the sanctioned `UPDATE tabFile JOIN … SET cloud_storage_object` (`:418-424`) then links those Files to the *wrong* CSO. `INSERT IGNORE` on refs silently drops a ref instead.
- Failure scenario: one or two File rows in the 1.2M corpus end up pointing at another file's content, with no error anywhere and no conflict row.
- Minimal fix: name both high-volume tables deterministically (`Cloud Migration Object.name = sha1(campaign||url_hash)`, `File Ref.name = sha1(campaign||file)`) — this removes the collision class *and* makes the upserts idempotent by construction; or drop bare `ODKU`/`IGNORE` in favour of explicit `SELECT`-then-`INSERT` keyed on the business unique.

## OPEN RISKS
1. `tabFile.content_hash` index is not permanent: A24 suppresses the Property Setter that `frappe.db.add_index` creates precisely to survive schema sync (`/home/user/v15/apps/frappe/frappe/database/mariadb/database.py:413-435` — comment "Ensure that DB migration doesn't clear this index"), so any re-sync of core `File` drops it (`frappe/database/schema.py:254-256` → `frappe/database/mariadb/schema.py:100-105`) and `install.after_migrate` rebuilds all 1.2M rows inside the migrate window; the "ALGORITHM=INPLACE, no table lock" claim is only MariaDB's implicit default (frappe emits a bare `ALTER TABLE … ADD INDEX IF NOT EXISTS`), and the required metadata lock still queues every `tabFile` query behind any long-running transaction.
2. CLASSIFY step 4 self-joins on `db_content_hash`, which is in no index in §2.3's `on_doctype_update` list (`.../design/migration-engine.md:300`) — an unindexed self-join over 1.2M rows; steps 2/5 are single non-resumable `GROUP BY` statements that can outlive the 3600 s job timeout and restart from zero.
3. `save_file(content=…, overwrite=True)` relinks only the mutated row (A2), so other File rows legitimately sharing that `file_url` keep the old CSO — `find_file_by_url` (`/home/user/v15/apps/frappe/frappe/core/doctype/file/utils.py:430-443`) returns the first *readable* row, so one URL can serve old or new bytes depending on who asks; A16 relinks hash-siblings but not URL-siblings.
4. `UNIQUE(s3_key)` omits `bucket` while the key is derived from `key_prefix/site/sha256` only (`.../design/runtime-storage.md:196,245`) — changing `bucket` (or `key_prefix`) after go-live makes every `ensure_cso` raise `DuplicateEntry` with a re-fetch that finds nothing; make both fields immutable once any CSO exists, or add `bucket` to the key.
5. The daily GC/orphan sweep and the "Local bytes remaining"/"Files migrated %" Number Cards are specified with no pagination, LIMIT or cache (`.../design/runtime-storage.md:§3.1/§12`, `.../design/delivery-platform.md:304`) — per-CSO recount over ~1M rows plus full `tabFile` aggregates on every workspace load.

## OPEN BUSINESS DECISIONS
1. **Maintenance-window and DB-host capacity sign-off**: the migration needs ~10–15 GB transient headroom on the production MariaDB datadir/binlog volume (B4) and adds an index rebuild on a 1.2M-row hot table to the `bench migrate` window. Only the business owner can accept that window and the storage spend.
2. **A18 default-ON rewriting of business-document fields** during legacy adoption (parent `Attach`/`Attach Image`/`image_field` values are updated in place, plan `:477-481`): this mutates live business records for availability reasons. Blast radius and rollback expectation need explicit owner approval, not an engineering default.
3. **Presigned-URL bearer exposure for statutory data**: `private_presign_ttl = 300 s` means a GST/e-invoice attachment URL is shareable, un-IP-bound and un-revocable for that window. Acceptable-risk call for a regulated corpus belongs to the owner (the alternative — proxying bytes through Python — costs throughput).

## VERDICT
**APPROVE WITH CHANGES.** Across my four dimensions the amended architecture holds: A1/A2/A16 close the URL-only and overwrite paths, A6/A14 make the refcount conservative, A7/A15 stop status fabrication, and the 1.2M-row snapshot sizing is defensible for the tables themselves. What survives are five bounded, local defects — a `deleted`-tombstone hole in `ensure_cso` (silent content loss on re-upload), unbounded boto timeouts with no breaker in the request path (an S3 outage becomes a site outage), a batch-finalisation gap that strands every transiently-failed object, a missing DB-capacity gate before a multi-gigabyte snapshot on the live DB, and random 10-char PKs combined with `ODKU`/`INSERT IGNORE` upserts. None requires re-architecting; all five should be bound as amendments A25–A29 with tests (re-upload-after-GC, breaker-under-injected-outage, partial-batch-residue, preflight-refusal, deterministic-name idempotency) before P2/P5 start.
