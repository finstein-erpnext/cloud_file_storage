# Deployment Runbook (skeleton — completed in P8; queue prerequisite is authoritative HERE)

## Dedicated migration queue (REQUIRED before any campaign)

The `cloud_migration` RQ queue must exist before `start_migration` will run
(`get_queues_timeout()` is lru_cached — frappe/utils/background_jobs.py:41-56 — so every
web/worker process must be restarted after the config change).

1. `sites/common_site_config.json`:
```json
"workers": { "cloud_migration": { "timeout": 3600, "background_workers": 2 } }
```
2. Dedicated worker process:
   - Procfile (dev): `worker_cloud_migration: bench worker --queue cloud_migration`
   - Production: `bench setup supervisor` regenerates a per-queue program
     (`numprocs` = background_workers; note `stopwaitsecs == timeout` — keep batch
     wall-time well under it).
3. Restart all processes (`bench restart` / supervisorctl).
4. Never point generic `bench worker` (no `--queue`) at production expecting isolation —
   custom queues rank last in its strict priority order.

Fallback: `start_migration --force-fallback-queue` runs on `long` with persistent loud
warnings. Never silent.

### On frappe v16, two extra steps

Both are silent if skipped — nothing raises, the campaign is just slower or less isolated.

5. **Set the scheduler tick back to 60s.** v16 raised the default from 60s to **240s**
   (`DEFAULT_SCHEDULER_TICK`, `frappe/utils/scheduler.py`). A `* * * * *` cron entry cannot
   fire more often than the tick, and `migration.engine.dispatch_tick` is the crash-recovery
   watchdog — the only thing that reclaims a batch whose worker died after the CAS. At 240s
   that recovery is four times slower.
```json
"scheduler_tick_interval": 60
```
   `dispatch_tick` reports the tick it actually observed and logs a warning while a campaign is
   running, so a bench left at 240s is visible rather than merely slow. Note that v16 skips its
   clock-aligned sleep whenever the tick is not the default, so pinning 60 also opts out of
   alignment — which is the v15 behaviour this app was measured against.

6. **Do not enable the NOFORK worker for `cloud_migration`.** v16 adds an opt-in non-forking
   worker (`FRAPPE_BACKGROUND_WORKERS_NOFORK`, used by `bench worker-pool`). Jobs then share one
   process, so module-level state and `frappe.flags.in_migration_job` leak between batches, and
   its exception handler turns a `JobTimeoutException` into worker shutdown — which would kill
   the worker that was about to run the backup retry that `backup/tasks.py` re-raises to
   schedule. `bench worker --queue cloud_migration` (the documented path above) still forks and
   is unaffected.

## S3 buckets (live + backup)
- Live bucket: private; Block Public Access ON (**after** legacy raw-URL adoption — A18);
  versioning ON with `NoncurrentVersionExpiration >= restore_window_days` (A27);
  lifecycle rule `AbortIncompleteMultipartUpload: 7 days`; storage classes
  STANDARD/STANDARD_IA/INTELLIGENT_TIERING only.
- CloudFront-OAC distribution scoped to `pub/*` when `cdn_base_url` is used.
- Backup bucket: separate from the live bucket (validated); lifecycle rules generated by
  the app are prefix-scoped and merged with existing rules.
- IAM: prefer instance-role/default chain; least-privilege policy sample lands here in P8.

## SECURITY — private files served off disk from the PUBLIC site tree (upstream frappe)

**Check this before go-live on every site, including sites that never install this app.**

**The vector.** Core's `File.make_thumbnail` writes every thumbnail to
`get_site_path("public", thumbnail_url.lstrip("/"))`
(`frappe/core/doctype/file/file.py:463`). A private file's thumbnail URL is
`/private/files/<name>_<suffix>.<ext>`, so the file lands at
`sites/<site>/public/private/files/<name>_<suffix>.<ext>`. bench's nginx template answers
`location /` with `try_files /<site>/public/$uri @webserver`
(`bench/config/templates/nginx.conf:91`), so **a GET of that URL is served off disk to an
unauthenticated caller, before any frappe process runs** — no session, no permission check,
no access log. The `location ~ ^/protected/(.*)` block in the same template is `internal`;
it exists for `X-Accel-Redirect` and does not guard `/private/...` requests. Core's own
`delete_file` looks for that thumbnail in `private/files/`
(`frappe/utils/file_manager.py:317-322`), so it is also orphaned when the File is deleted —
the same inconsistency seen from the other end.

**This predates Cloud File Storage and is not caused by it.** A stock frappe site with no
apps installed has it.

**What this app does.** Rows it manages are fixed: a private thumbnail is written to
`private/files/`, the privacy flip moves an existing one out of the public tree (moved,
never deleted), and the private serving path serves it behind the permission gate. Rows it
does not manage — pre-install rows, the LOCAL_OPERATIONAL doctypes, any row on a LOCAL_ONLY
site — keep core's behaviour, because LOCAL_ONLY is contractually byte-identical to core and
because this app does not relocate files it does not own.

**Detect.** Reported on every `bench migrate` (an Error Log row) and in the Settings health
panel (`test_connection` → `public_private_residue`). By hand:

```
find sites/<site>/public/private -type f
```

**Remediate (operator action — the app will not do it for you).**
- A thumbnail of a **cloud-backed** file can simply be deleted; it is regenerated on demand
  and the derived object already serves it.
- Anything else: move it to the matching path under `sites/<site>/private/files/`, which is
  where core's own `delete_file` and `send_private_file` expect it.
- Then confirm `find sites/<site>/public/private -type f` is empty, and consider a
  belt-and-braces nginx `location ^~ /private/ { internal; }` guard so the case cannot
  reappear from any app.

**Upstream.** Written up for frappe's security process in
`docs/security/upstream-frappe-private-thumbnail-disclosure.md`, which carries the evidence,
the reproduction and a suggested patch; tracked in DECISIONS.md (post-v1 backlog). Do not
wait for an upstream fix before running the remediation above.

## Adopting an external `frappe_s3_attachment` 0.2.x install (A21)

**Do these in order. Step 4 cannot be run before step 3**, and that is the whole point of the
procedure: `bench migrate` reads `installed_apps` *unfiltered*
(`frappe/modules/patch_handler.py:89`, `frappe/model/sync.py:43`), so on a site that still
names the vanished module it raises `ModuleNotFoundError` before any patch of ours can run. A
patch cannot fix the thing that stops patches from running.

Proven end to end on a synthetic legacy site — see
`docs/evidence/p8-legacy-install-rehearsal.md`.

0. **Take a database backup, and verify you can read it.** This procedure rewrites
   `installed_apps` on a live site, and step 4 then runs every patch
   this app ships. Everything below is designed to be additive and was rehearsed end to end,
   but "additive" is a property of the code, not of the afternoon. This app's own A29 preflight
   **refuses to start a migration campaign** without a recent dump; the procedure that has to
   precede that campaign should not ask for less.

   ```
   bench --site <site> backup --with-files
   ```

1. **Drain the RQ queues.** In-flight jobs serialise the old dotted paths
   (`frappe_s3_attachment.controller.run_migrate_existing_files`) and will
   `ModuleNotFoundError` in the worker after the swap.
2. **Fix the bench.** Update `sites/apps.txt` and `sites/apps.json`;
   `pip uninstall frappe_s3_attachment`; `pip install -e apps/cloud_file_storage`. Confirm
   `bench --site <site> list-apps` succeeds before going further.
3. **Run the bootstrap, out of band:**

   ```
   bench --site <site> cfs-adopt-legacy-install --dry-run   # shows exactly what will change
   bench --site <site> cfs-adopt-legacy-install
   ```

   It swaps the `installed_apps` entry (taking the fork's slot, so app order is preserved),
   reports what fork residue it found, and previews the settings adoption will carry over. It is additive, idempotent, and a no-op on a site that was never a legacy
   install. The equivalent entry point for scripting is
   `bench --site <site> execute cloud_file_storage.legacy_install.bootstrap`.
4. **`bench --site <site> migrate`.** Two guarded patches finish the job:
   `v1_0_0.adopt_legacy_fork_install` (`[pre_model_sync]`, in case step 3 was skipped on a site
   that reached this app another way) and `v1_0_0.link_legacy_fork_objects`
   (`[post_model_sync]`), which copies the fork's settings and ignored-doctype list into
   **Cloud Storage Settings**, and mints one `legacy_unverified` **Cloud Storage Object** per
   fork key, linking its File row.
5. **Check the settings.** The fork's bucket, region, endpoint, folder (as `key_prefix`),
   access key and secret are carried over, and `use_default_credential_chain` is turned off if
   a key **and a usable secret** were adopted. Anything you had already configured on the new
   settings is left alone.

   **If the fork's Secret Key could not be retrieved** — its `__Auth` row was deleted, or was
   never written — adoption still succeeds, and deliberately so: the alternative is a migrate
   that dies on a credential-pairing error. The site comes up on the default credential chain
   holding an Access Key ID it cannot use, and an Error Log titled *"adopted an access key with
   no secret"* says so. Pick one:
   - enter the **Secret Access Key** beside the adopted key and clear **Use Default Credential
     Chain**; or
   - clear the **Access Key ID** and keep using the instance's credential chain.

   Setting one without the other is refused by the settings validator, which is the point.
   Two fork fields have no home in the frozen schema and are reported rather than migrated:
   `delete_file_from_cloud` (this app defers every physical delete to GC; there is no setting
   that turns that off) and `timeout_for_migration_job` (its endpoint is gone).
6. **Promote the adopted objects — nothing does this for you.** They are `legacy_unverified`
   on purpose: adoption moves no bytes and computes no hash, so nothing claims to be verified.
   Promotion is a **manual** call and there is no scheduler entry for it; an adopted site left
   alone keeps every object at `legacy_unverified` indefinitely. Run it a page at a time:

   ```
   bench --site <site> execute \
     cloud_file_storage.migration.adoption.promote_adopted_batch --kwargs "{'limit': 100}"
   ```

   Each call streams the object back, hashes it, and promotes it to `verified` only if the
   bytes agree. Repeat until `candidates` comes back 0. (`docs/runbooks/migration.md` says the
   same; if these two ever disagree, this is the one that has been executed.)

### What the bootstrap does not do

- **It does not rewrite `tabFile.file_url`.** Old
  `/api/method/frappe_s3_attachment.controller.generate_file?key=…` URLs keep resolving through
  the `override_whitelisted_methods` remap, forever (A10) — and they also live in business
  fields, emails and bookmarks where no patch could reach them. Canonicalising them is an
  adoption *campaign*, with aliases and audit rows, not a migrate.
- **It does not rewrite `tabPatch Log`.** Our patches are new module names that cannot collide
  with a fork entry, so nothing re-runs; rewriting the prefix would only forge history.
- **It deletes nothing, and it writes nothing to the fork's own records.** The fork's
  `Module Def`, its DocType rows, its `tabSingles` values and its `__Auth` secret all survive,
  and they keep surviving: an earlier revision repointed `Module Def.app_name` at this app,
  which would have made the fork's module an uninstall target — `bench uninstall-app` selects
  what it destroys by exactly that column — and it was dropped once the benefit turned out not
  to exist on any supported frappe version. Frappe's own orphan reaper leaves the fork DocTypes alone too —
  it treats `ImportError` as the orphan signal and this path raises `DoesNotExistError`.
- **It makes no S3 call.** A migrate that needs the bucket reachable is a migrate that fails
  during an outage.
